# 추천 점수와 선택 규칙

Readytogo의 추천은 전부 결정적인 코드다(LLM 없음). 이 문서는 숙소·식당·관광지를 어떻게 점수 매기고, 화면의 두 선택지를 어떻게 고르는지 정리한다. 원본 결정 기록은 [CLAUDE.md](../CLAUDE.md)에 있다.

## 1. 여행 목적 → 예산 배분과 일정 밀도

항공료(검색된 실제 최저가)를 뺀 **나머지 예산**을 목적별 비율로 나눈다.

| 목적 | 숙박 | 식비 | 기타 | 하루 관광지 수 |
|---|---|---|---|---|
| 휴양 | 0.55 | 0.25 | 0.20 | 2 |
| 관광 | 0.40 | 0.25 | 0.35 | 4 |
| 맛집 | 0.35 | 0.45 | 0.20 | 3 |
| 액티비티 | 0.35 | 0.25 | 0.40 | 3 |
| 선택 없음 | 0.45 | 0.30 | 0.25 | 3 |

- 여러 목적을 고르면 평균을 낸 뒤 비율 합이 1이 되게 정규화하고, 관광지 수는 반올림한다. 예) 관광 + 휴양 → 0.475 / 0.25 / 0.275, 하루 3곳.
- 도착일·출국일은 목적과 무관하게 1곳.
- 목적마다 찾는 장소 종류도 다르다(휴양 = park, spa, beach, garden…, 관광 = museum, historical_landmark…).
- 코드: `domain/purpose/PurposeProfile.kt`, `PurposeAttractionTypes.kt`

## 2. 숙소·식당 점수

```
점수 = 0.5 × 평점 점수 + 0.5 × 동선 점수          (0 ~ 1)
```

**평점 점수** — 리뷰 수로 보정한 평점(베이지안 평균)을 5로 나눈다.

```
보정 평점 = v/(v+m) × 별점 + m/(v+m) × 4.0        v = 리뷰 수, m = 50
```

리뷰 3개짜리 5.0점이 리뷰 2,000개짜리 4.5점을 이기지 않게 하기 위해서다.

**동선 점수** — 기준점에서 멀수록 떨어지고 10km에서 0이 된다.

```
동선 점수 = max(0, 1 − 거리(km) / 10)
```

| 대상 | 기준점 | 이유 |
|---|---|---|
| 숙소 | 일정에 **실제 배치된** 관광지의 중심 | 여행 내내 오가는 곳. 가지도 않을 곳은 계산에 넣지 않는다 |
| 끼니 식당 | 바로 앞 일정 → 식당 → 바로 뒤 일정의 **우회 거리** | 한 번 들르는 곳. 중심에 가까워도 앞뒤와 반대 방향이면 지도 선이 교차한다 |

중심점은 위도·경도 각각의 **중앙값**이다. 평균을 쓰면 외딴 한 곳(도쿄 일정의 하코네)이 중심을 끌고 간다. 거리는 하버사인 직선거리 — 상대 비교에는 충분하고 경로 API 호출이 없다.

코드: `domain/recommend/Scoring.kt`

## 3. 관광지 점수

```
관광지 점수 = 0.5 × 평점 점수 + 0.5 × 동선 점수 + (목적과 맞으면 0.15)
```

- 가산점은 가중 합산 뒤에 더한다(최대 1.15, 순위용).
- 0.15인 이유: 평점 ★0.5 차이가 점수로 약 0.05라, 비슷한 평점끼리는 목적이 이기고 평점이 크게 벌어지면 평점이 이긴다.
- `tourist_attraction`은 검색에는 쓰지만 목적 일치 판정에서는 뺀다. 거의 모든 관광지에 붙는 범용 타입이라, 판정에 쓰면 메이지 신궁이 "맛집"으로 통과했다.
- **점수로 먼저 뽑고 나서 동선을 엮는다**(최근접 이웃). 순서가 반대면 점수 낮은 곳이 사슬에 끼어 들어온다.

코드: `domain/recommend/AttractionScoring.kt`, `data/repository/mock/MockItineraryRepository.kt`

## 4. 두 선택지 규칙 (숙소·식당 공통)

화면에는 항상 두 곳이 나온다. 1번은 점수 최고(단 **예산의 2배를 넘는 곳은 제외** — 고를 수 없는 추천은 칸만 차지한다. 2배 안에 후보가 없으면 제한 없이 1등). 2번은 1번의 상황에 따라 기준이 바뀌고, 그 기준을 이름표로 붙인다.

| 1번의 상태 | 2번 기준 | 이름표 |
|---|---|---|
| 예산 초과 | 예산 안에서 점수 최고 (없으면 가장 싼 것) | 예산 내 |
| 예산 내 | **1번보다 싼 것 중** 점수 최고 | 가성비 |
| 예산 내 + 더 싼 후보 없음 | 동선 점수 최고 | 동선 우선 |
| 후보가 하나뿐 | — | 대안 없음 |

1번이 이미 예산 안인데 "예산 내 2등"을 보여주면 2번이 더 비쌀 수 있어 이름표와 내용이 어긋난다. 그래서 그때는 "더 싸게 가면 무엇이 있나"를 보여준다. 두 선택지 모두 리뷰 수와 기준점까지의 거리를 함께 표시한다 — 점수만 보이면 왜 추천됐는지 알 수 없다.

코드: `domain/recommend/Recommender.kt`

## 5. 끼니 고르기 — 예산을 먼저 지키고 평점을 양보한다

```
1. 예산 내 + 평점 4.0 이상
2. 예산 내 + 평점 3.5 이상
3. 예산 초과 허용 (빨간 "예산 초과" 표시)
4. 그래도 비면 반경 3배로 한 번 더 검색
5. 끝내 없으면 "근처 추천 식당 없음" 자리를 남긴다
```

- 두 선택지가 다 채워지는 단계를 먼저 찾는다.
- 한 번 추천한 식당은 여행이 끝날 때까지 다시 쓰지 않는다.
- 아침은 카페·베이커리, 저녁은 술집도 허용 — 아침에 오마카세가 뜨지 않게 끼니별로 어울리는 곳만 본다.
- 식당 검색은 날짜별로 하되, 중심이 3km 안인 날끼리는 검색을 공유한다. 후보가 처음부터 모자란 날은 반경 2배로 다시 찾는다.

코드: `domain/plan/TripPlanner.kt`

## 6. 관광지 교체 후보

- 날마다 일정에 들지 않은 검색 결과 중 **그날 관광지 기준** 점수 상위 5곳 + (없으면) 그날 동선 중심 5km 안의 실내 1곳.
- 교체 기준은 `indoor`(실내) 또는 `near_prev`(바로 앞 일정에 더 가까운 곳). 다른 날에 이미 있는 곳과 그날 쉬는 곳은 뺀다.
- 실내/실외는 Places 본업 타입 표로 판정하고, 사찰·신사처럼 애매한 곳은 판정을 미룬다.

코드: `domain/plan/AttractionAlternatives.kt`, `domain/edit/PlaceSwap.kt`, `domain/purpose/IndoorOutdoor.kt`
